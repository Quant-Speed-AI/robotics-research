# GPT-6 机械臂绘画：项目核验与 XLeRobot 移植方案

核验日期：2026-10-02。目标：结合 1–5 万元 MVP 预算、昆明学校/培训/展厅及文旅资源，判断最近演示的技术含量和可复现路径。本次为公开资料及关键源码审阅，未调用收费模型、运行仿真或测试实体机器人。

## 判断

值得做一个固定工位的绘画 MVP。与 XLeRobot 最贴近的是 Thijs 的 SO-101 实机画金门大桥；最容易检查模型调用链的是 astra-paints；最适合学习接触控制的是 dimentary 的鸽子绘画仿真。三个项目解决的层次不同，不能把演示能力合并成一个已经可买、可直接部署的产品。

建议第一版：单个 SO-101 从臂、固定画板、弹性笔架、俯视相机、现有电脑，完成单色文旅明信片。先验证画出来的质量、速度和付费意愿，再加 XLeRobot 底座及第二只手。以下产品和预算建议均为工程判断，不是现成项目业绩或供应商报价。

## 2. Thijs：为什么最适合参照 XLeRobot

作者说明用了借来的 SO-101，并给予初始锚点；要求模型规划约一分钟动作、后台观察与调整；在各轮之间、有时执行期间给予人工反馈，让模型更新自身指令。这里的“一分钟”是动作规划片段，不是完成一幅画的时间。[作者原文镜像](https://zamantika.com/fr/cdngdev/status/2097339677128982873)

可以确认的机制是“观察—计划—执行—反馈修正”，且包含人工辅助。不能确认其 MCP 接口、ROS 使用、逆运动学实现、控制频率、API 消耗、总作画时间、力传感器、持续成功率。没有模型权重更新证据，所以不能把反复调整描述成已经训练出新的绘画模型。

迁移价值：XLeRobot 官方建立在 LeRobot、SO-100/SO-101 等项目之上，机械臂生态接近。相同硬件家族并不保证相同电机电压、结构尺寸、零位和末端安装参数；这些必须按实物核对。[XLeRobot 官方仓库](https://github.com/Vector-Wangel/XLeRobot)

## 3. astra-paints：模型在线规划，控制器完成运动

实际调用链：

```text
主题 + 当前画布图像
  → AstraPaintAgent.plan()
  → OpenAI 调用，要求 JSON 笔画
  → execute_strokes()
  → 逆运动学、线段插值、抬笔/落笔
  → MuJoCo 执行 + 软件画布更新
  → 下一轮观察
```

`agents/astra_agent.py` 将当前画布编码为 PNG 图像；每次要求 3–8 条笔画，每条包含颜色和二维点，另有完成标记。模型名默认为 `gpt-6-astra`，可由配置覆盖。支持把上次失败图片与文字评价送入第一轮。费用计算采用源码内硬编码价格，不应拿它当当前官方报价。[模型调用源码](https://raw.githubusercontent.com/riyer8/astra-paints/main/agents/astra_agent.py)

`agents/base.py` 负责抬笔到起点、约 2 mm 间隔插值、求解关节角和执行。`sim/world.py` 是两根连杆的平面逆运动学加一个升降控制量，不能直接替代 SO-101 的空间运动学。[执行源码](https://raw.githubusercontent.com/riyer8/astra-paints/main/agents/base.py)、[运动学源码](https://raw.githubusercontent.com/riyer8/astra-paints/main/sim/world.py)

关键限制：`sim/canvas.py` 直接在像素画布上盖圆形色点，未模拟真实颜料、蘸水、换色和干湿混合。执行代码画色点的条件也不是完整的真实接触力判据。因此它验证的是绘画规划循环和简化运动，不证明真实毛笔也能得到同样结果。[画布源码](https://raw.githubusercontent.com/riyer8/astra-paints/main/sim/canvas.py)

移植时可借鉴计划接口与日志结构；必须重写实际相机观察、SO-101 运动学、笔尖标定和硬件执行层。JSON 格式正确也不等于轨迹可执行：需要本地验证点数量、数值范围、可达性、速度及中断处理。

## 4. dimentary：物理接触更深入，但 GPT 在开发阶段

官方仓库明确说早期实验由 Astra 帮忙搭环境、写控制器，作者参与任务设置和反馈；运行/回放在本地进行，不调用模型 API。[仓库说明](https://github.com/dimentary/llm-robotics-playground)

鸽子实验中铅笔已经放在手中，靠接触与摩擦保持；跟随预先描出的九条路径。作者报告九笔耗时 173 个仿真秒、路径误差中位数 0.149 mm。它们是该仿真记录的指标，不能视为 SO-101 实机精度或吞吐量。画面还放大了线宽，视频为 4 倍速。[实验说明](https://raw.githubusercontent.com/dimentary/llm-robotics-playground/main/experiments/dove-drawing/README.md)

`controller.py` 使用雅可比矩阵的阻尼伪逆求解位置及姿态，并做关节限位和插值。`writer.py` 读取模拟器中的笔尖位置与接触力，每 0.02 仿真秒更新控制：XY 修正路径偏差、Z 修正压纸程度。[控制器](https://raw.githubusercontent.com/dimentary/llm-robotics-playground/main/experiments/dove-drawing/controller.py)、[笔尖控制](https://raw.githubusercontent.com/dimentary/llm-robotics-playground/main/experiments/dove-drawing/writer.py)

迁移难点：模拟器提供精确状态和接触力，普通 SO-101 实机没有被上述代码接入的同等测量。需要相机/标定估计笔尖、实际力传感器或机械顺应结构。首版圆头笔用弹性笔架保持适当接触，更容易工程化；这只提供被动顺应，不能宣传为闭环力控。已有图案数据的许可也与控制代码分开，最好使用自己的昆明元素图案。

## 5. WLKATA：最接近可交付的线稿流程

官方 README 的路线是用户先用图生图工具生成简洁线稿、下载图片，再由本地绘画模块处理。关键源码是 OpenCV 图像处理、轮廓简化、坐标缩放以及机械臂 SDK 命令。模型没有实时决定每一个关节角。[官方仓库](https://github.com/wlkata/WLKATA-AI-Drawing-Extension)

完整源码审阅另见同目录 `06_WLKATA绘画源码核验.md`。适合借鉴图像到路径的处理，但 WLKATA 的执行命令不能直接下发给 SO-101。

## 6. 推荐给 XLeRobot 的实际架构

以下为建议设计，不是对上述作者未公开源码的推断。

```text
游客主题/照片/姓名
  → 模型生成简化构图或线稿
  → SVG/轮廓转路径，限制笔画数量
  → 纸面坐标 → 机器人坐标 → 笔尖位姿
  → 本地逆运动学、轨迹平滑、限位
  → LeRobot/Feetech 驱动 SO-101
  → 俯视相机检查漏画与偏移
  → 必要时模型规划补画，或者本地暂停
```

采用圆头笔时，任务可优先约束笔尖位置和笔轴方向，放松绕笔轴旋转；SO-101 的五个运动关节加夹爪适合研究此类受限任务。五关节不保证全幅纸面处处可达，更不保证任意毛笔姿态；先验证中心小画区，避开伸直边界。[官方关节与驱动说明](https://huggingface.co/docs/lerobot/so101)

| 模块 | 第一版建议 | 需要解决的实际问题 |
|---|---|---|
| 机械臂 | 单个从臂，固定到刚性桌面 | 晃动、回差和伸展刚度 |
| 末端 | 防旋转笔架 + 弹簧浮动圆头笔 | 笔滑移、漏画、压纸过深 |
| 画板 | 小范围固定定位槽 | 每张卡片重复定位 |
| 相机 | 独立俯视相机，先固定曝光光照 | 纸面映射、笔迹识别和遮挡 |
| 模型 | 构图、计划、分段视觉检查 | 少量高层调用即可，避免依赖网络逐点驱动 |
| 控制器 | 确定性执行及恢复状态机 | 检查路径、限制动作、记录失败、停机与恢复 |
| XLe 底座 | 第一版固定，后续站间移动 | 外部桌面须重新定位；车载画板仍需稳定支撑 |
| 第二只手 | 后期再做递卡或换笔 | 不应在绘画验证前增加碰撞/抓纸问题 |

两种标定不能混淆：LeRobot 电机零位/范围标定只统一关节读数；画画还要标定纸面相对底座的位置、纸面高度、笔尖相对夹具的偏移。更换笔长或笔架后需复核。相机对纸面的二维映射不能单独替代完整的机器人/笔尖几何标定。

工具接口可封装为 `observe_canvas`、`plan_preview`、`draw_strokes`、`lift_pen`、`stop`。可用普通函数调用或 MCP；MCP 是接口封装，不能替代运动学与实时控制。执行中的取消、网络断连和不可达点必须由本地层处理。具体抬笔或断电策略须按实际安装验证，不能假定断电后手臂不会下落。

## 7. 1–5 万元预算下的 MVP 与验收

第一版优先“昆明主题单色明信片”：用户选海鸥/花卉/地标主题，可加姓名；模型生成受限构图；机械臂现场绘制，工作人员负责装卸纸。图案是建议，不代表已经获得任何景区或机构订单。

预算先用上限约束：桌面验证阶段暂定控制在 1 万元内、复用现有电脑；剩余预算用于控制软件、笔架/画板迭代、外观和试点。该数值是投入上限，不是本轮核实的可采购整套报价。只为绘画不必先购买完整双臂移动平台。

建议验收顺序（以下全是目标，不是现有性能）：

1. 无模型依赖的直线、圆、方框、抬落笔测试：中心小画区连续 20 张，记录漏线、重影和偏移。
2. 10 种固定图案各重复 3 次：统计合格率、平均/较慢出画时间、人工接管次数。
3. 接入主题生成与路径预览：固定图案与新图案采用同一执行层，区分生成问题和机械问题。
4. 接入相机复查：先识别明显失败，再研究有限补画，避免反复涂改把纸画坏。
5. 到学校/展厅或文旅合作场地试点：记录付费转化、围观停留、工作人员工时、耗材、报废、模型费用和场地方分成。

商业测算要用实测节拍：如果每单总周期为 5 分钟，理论上限是 12 单/小时；设备等待、换纸和返工会继续降低吞吐。这是算术示例，不是机器人实测速度。先验证游客为什么愿意购买现场过程与纪念品，再决定扩大投入。

## 8. 复现优先级

1. 看 Thijs 实机原帖，确定所期待的实体展示效果。
2. 阅读 astra-paints 的模型输出/执行接口，理解如何把模型变成可控的笔画规划器。
3. 借鉴 WLKATA 的线稿路径流程，做可重复的单色基线。
4. 使用 dimentary 的控制器学习接触与笔尖反馈，不直接将仿真精度或控制参数搬到 SO-101。
5. 最后集成 XLeRobot 的移动和双臂能力。

核心决策：可把“AI 绘画互动”作为 XLeRobot 的首个应用来验证。短期成功主要取决于标定、笔尖接触、轨迹与产品设计；更强模型可以改善构图和判断，但不能替代这些环节。
