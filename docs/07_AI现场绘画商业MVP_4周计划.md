# AI 现场绘画商业 MVP：4 周推进计划

更新日期：2026-10-02。本文把既有机器人调研收敛为一个可公开演示、可收费验证的产品计划。排期是目标，不代表硬件已经到位、接口已经验证或商业结果已经达成。涉及支付、图像服务和硬件控制的实现，均需使用各自正式账号、密钥与设备配置。

## 1. 产品目标与闭环

目标是做出“AI 当面为用户创作一幅作品”的现场体验，而不是先堆叠复杂机器人能力。用户扫码、选择或输入内容、确认预览并支付；系统生成适合绘制的图像和轨迹，将付费任务排入队列；机械臂执行并完成作品，现场交付给用户。

```text
扫码进入 H5 → 选择主题/输入内容 → 生成线稿预览 → 用户确认并支付
    → 生成可执行路径 → 任务排队 → XLerobot 执笔 → 完成检查 → 交付作品
```

### MVP 成功标准

- XLerobot 能稳定拿笔，完成简单图形、线稿和受控风格的卡通画。
- 图像能转换为经过校验的机器人轨迹，越界或不可达任务不会直接执行。
- 用户可扫码进入页面、确认作品并完成支付；支付成功后任务自动入队。
- 任务能够从生成走到绘制、完成或明确失败状态，并保留日志。
- 单幅目标耗时 3–10 分钟；连续服务 10 位用户期间无严重故障。
- 第 28 天在真实场景进行首次收费测试，并记录真实漏斗和服务数据。

这些是验收目标，不是现有性能承诺。现场收费前应先完成设备安全检查、人工急停验证、异常停机与订单退款/人工处理流程。

## 3. 技术优先级

P0 是“SVG/笔画路径 → 坐标变换 → 可达性与限位检查 → XLerobot 稳定作画”。GPT、支付和页面都依赖一个可靠的执行器。首版不让大模型直接输出关节命令，也不让未校验的生成轨迹直接驱动机械臂。

```text
SVG/Path
  → 纸面到机器人坐标变换
  → 路径简化、排序和采样
  → 逆运动学/可达性/关节限位检查
  → 确定性抬笔、落笔和移动指令
  → 执行、状态回报、急停与故障记录
```

建议先提供稳定的 `draw_svg(path)` 接口。底层执行层应支持预览、空跑、取消、急停、任务进度和明确错误；具体运动 API 与机械参数需按实际 XLeRobot 版本确认。加压式画笔首版应采用机械顺应设计，不宣称闭环力控，除非已安装并验证力传感器和控制链。

AI 上游可拆为：用户描述理解、受限构图/线稿生成、路径转换与用户预览。转换阶段应处理 Douglas–Peucker 简化、短路径过滤、重复路径清理和空移排序，但不以固定点数（如 600–1000）作为普适承诺；路径预算应由实测速度、画质和 3–10 分钟时限决定。所有路径需做范围、点数、速度、可达性和执行时长校验。

## 4. 每周推进与验收

### 第 1 周：建立可靠的 SVG 作画基线

**阿甘：** 固定底座和画纸；确定画板尺寸、笔夹和笔尖顺应；记录工作范围、回零和更换画笔后的复标方法；验证落笔/抬笔高度与纸张定位。

**小柳：** 先绕过 GPT，解析 SVG Path，建立纸面坐标变换与 `draw_svg(path)`；加入轨迹预览、限位检查、抬落笔和执行日志。

**测试顺序：** 直线 → 正方形 → 圆 → 五角星 → `HELLO` → 简单卡通脸。先做空跑，再用低速、轻压力在限定画区绘制。

**验收：** 输入 `smile.svg` 后，机械臂能自主完成移动、落笔、绘制、抬笔并返回完成状态。记录连续重复绘制的偏移、漏线、卡顿和人工接管次数。不要直接把 A4 全幅误差目标当作已验证规格；先按实机可达区域确定画幅和公差。

### 第 2 周：接入 AI 生成与可控路径

**阿甘：** 评审线稿是否适合实体绘制，建立 10 个固定主题样例，反馈难画笔画、纸张和画笔问题。

**小柳：** 把自由文本转换为受限绘图描述；生成黑白、简洁、少阴影的线稿；转换为 SVG/Path，优化路径并提供用户预览、重生成和确认流程。

**验收：** 对固定主题和用户关键词各做一组离线/实机样例，统计可转换率、单幅耗时、路径长度和人工修复次数。模型输出无法安全转换时应退回固定模板或提示重试，不能下发未验证轨迹。

### 第 3 周：扫码、支付、队列与后台

用户页面先限定三类：AI 签名/简笔画、AI 卡通画像、AI 肖像（只有在样例质量和耗时达标后开放）。流程为扫码、选类型、输入文字/上传照片、生成预览、确认、支付、排队、绘制、完成通知/现场领取。

建议订单状态：

```text
CREATED → GENERATING → READY_FOR_CONFIRMATION → PAYMENT_PENDING
  → PAID → QUEUED → DRAWING → DONE
                                 ↘ FAILED / CANCELLED / REFUND_REQUIRED
```

支付回调必须做签名验证和幂等处理；以支付平台的正式回调作为入队依据，避免重复通知造成重复绘制。对生成失败、支付成功但任务未入队、设备离线、绘制中断和退款建立后台可见状态与人工处理入口。不要在公开仓库或前端代码中提交密钥、商户号私密配置或用户照片。

**验收：** 使用支付沙箱或经商户配置的测试流程，验证创建订单、支付成功/失败、重复回调、队列排序、取消和失败状态。正式收费需在支付商户资料、回调域名和实际设备环境就绪后进行。

### 第 4 周：真实场景收费验证

阿甘负责选择学校、展厅或文旅合作点，确定展示话术、定价试验和现场人员安排；小柳负责部署、监控、后台、队列及故障记录。首批建议只开放三种容易控时的产品。价格是假设，需现场测试：

| 产品 | 目标绘制时长 | 建议试测价格 |
|---|---:|---:|
| AI 签名/简笔画 | 2–3 分钟 | ¥9.9–19.9 |
| AI 卡通画像 | 约 5 分钟 | ¥19.9–39.9 |
| AI 机械臂肖像 | 5–10 分钟 | ¥39.9–69.9 |

**验收：** 公开演示并争取完成首次真实收费；测试连续 10 位用户服务，记录严重故障、人工接管、作画时长、重画/报废、支付与退款情况。观察路过人数、停留人数、扫码人数、付款人数和完成交付人数。漏斗统一口径：停留率=停留人数/路过人数，扫码率=扫码人数/停留人数，付费率=付款人数/扫码人数。

## 5. 每日任务板

每天把工作写成有负责人、验收条件和状态的具体事项。以下是启动模板，日期应按实际开工日填写。

| 日程 | 负责人 | 任务 | 验收标准 |
|---|---|---|---|
| Day 1 | 阿甘 | 制作笔夹并固定画板 | 笔固定 10 分钟无松动，纸张定位可重复 |
| Day 1 | 小柳 | 验证 XLeRobot 通信 | Python 控制机械臂完成低速安全小幅移动 |
| Day 2 | 阿甘 | 建立纸面/机械臂 XY 标定 | 记录工作区与重复定位误差；目标公差按实测确认 |
| Day 2 | 小柳 | SVG Path 解析 | 读取测试 SVG 并输出可视化折线 |
| Day 3 | 小柳 | Path 到安全动作 | 预览正方形轨迹，越界路径被拒绝 |
| Day 4 | 阿甘 | 画笔与连续线测试 | 记录断墨、漏画、纸张滑动和机械臂状态 |
| Day 5 | 两人 | 综合作画复测 | 自动绘制笑脸；保存任务日志和结果照片 |

后续每天沿用相同字段，任务拆到一个工作日内可验收的大小。遇到阻塞时记录原因、负责人和下一步，而不是记为“继续研究”。

## 6. 风险与放量闸口

- **轨迹和可达性：** 仅执行本地校验通过且经过预览的任务；设置软限位、低速测试、可触达急停和现场监护。
- **纸面定位和笔尖误差：** 标定机械臂零位与纸面坐标是两件事；换笔、笔夹或画板后复核。
- **队列与支付：** 订单入队必须幂等；设备离线、取消、退款及中途失败要能人工处理。
- **吞吐：** 3–10 分钟是目标范围。以实测含换纸、确认、失败重试的端到端时间计算产能，不用电机运动时间代替服务周期。
- **隐私：** 若支持上传照片，应明确告知用途和保留期限，限制后台访问并按约定删除；首版可先用关键词生成规避照片存储复杂度。
- **规模判断：** 先完成限定图案、固定画幅和连续服务验证，再扩展人像细节、第二只手或移动底盘。

## 7. 第 7/14/21/28 天共同里程碑

- **第 7 天：** 机械臂可自动绘制 SVG。
- **第 14 天：** 一句话生成可预览图案并由机械臂完成绘制。
- **第 21 天：** 扫码、测试支付、自动排队并执行绘画。
- **第 28 天：** 在真实场景完成首次收费测试并复盘数据。

以上里程碑是冲刺目标。若硬件通信、标定或实体路径质量未过关，应缩小可售图案范围并保留人工确认，不应以跳过安全/验收步骤来追赶日期。

## 8. 决策原则

第一版 Demo 可以是“AI 给你画一只专属小动物”：用户输入三个关键词（如“猫 / 朋克 / 程序员”），系统生成戴墨镜、穿朋克夹克、抱电脑的猫，机械臂绘制并写上祝福语。它比自由人像更容易控制复杂度，也能讲清现场体验。实际图案应使用自有或许可明确的素材。

产品对外表达为“AI 给你画一幅画”。后台可显示“正在构思”“正在绘制”等真实进度，但不要把虚构的模型思考过程包装成实际能力。顾客购买的是创作体验和可带走的作品；设备品牌与模型型号不是核心卖点。

**首要工程关口仍是 SVG/轨迹到 XLerobot 稳定作画。** 先把这一段做成可重复、可中断、可复盘的能力，再扩展模型、支付和商业场景。
